# Quality, Safety & Governance Requirements
## Project: EventCraft AI

---

### 1. Mandatory Quality & Safety Principles

These quality and safety directives are binding across all subsequent development phases (Phase 2 through Phase 9).

---

### 2. Detailed Principles

#### 1. Server-Side Input Validation
- **Requirement:** Every request received by backend route handlers or server actions must be validated against a strict Zod schema before processing.
- **Rule:** Never trust client-side data or assumptions. Sanitize strings, strip unexpected fields, enforce range limits (e.g., guest count $> 0$, budget $\ge 0$).

#### 2. Secrets & Credential Management
- **Requirement:** API keys (Gemini, OpenAI, Database credentials, Auth secrets) must strictly reside in server-side environment variables (`.env.local`).
- **Rule:** Never expose secrets with `NEXT_PUBLIC_` prefixes or commit `.env` containing live credentials to version control. The repository must maintain `.env.example` with dummy values.

#### 3. Strict Tenancy & Authorization
- **Requirement:** Every data query and mutation (read, update, delete) must enforce tenancy isolation.
- **Rule:** `where: { id: eventId, userId: session.user.id }`. Under no circumstances should an endpoint accept an `eventId` and mutate it without validating the authenticated session's ownership.

#### 4. AI Untrusted Input & Schema Integrity
- **Requirement:** All responses returned from GenAI models must be treated as untrusted input.
- **Rule:** Responses must be parsed through strict Zod schemas (`SafeParse`). If schema parsing fails, invoke a structured repair or fall back to standard domain templates.
- **Zero-Code Execution:** Never execute scripts, code strings, or SQL queries generated by an LLM (`eval()`, dynamic SQL, etc.).

#### 5. Prohibition of Fabricated Vendor & Pricing Claims
- **Requirement:** The AI assistant and application must never fabricate real-world vendor names, phone numbers, fake reviews, or invent unverified commercial rates presented as verified truth.
- **Rule:** The assistant provides *estimated industry-standard benchmark ranges* and *checklist categories* (e.g., "Typical wedding catering benchmark: $60–$120/head"). It must clearly label estimates as estimates. Real vendor data is only created when entered by the user or fetched through verified directory APIs.

#### 6. Distinction Between Estimates and Actual Ledger
- **Requirement:** Clear visual and semantic distinction in the UI between:
  - **Estimated/Allocated Budget** (planned target based on benchmarks or AI recommendations)
  - **Actual Expenses** (confirmed receipts, logged contracts, paid amounts)
- **Rule:** Overrun alerts must trigger when actual expenses surpass allocated thresholds.

#### 7. Explicit User Consent for Consequential Actions
- **Requirement:** Destructive operations (deleting events, regenerating plans which replace custom tasks, sending invitations, logging contracts) require explicit confirmation dialogs.
- **Rule:** No action that irreversible mutates user plans should occur without confirmation.

#### 8. Graceful Degradation & Resilience
- **Requirement:** If external AI services encounter rate limits, outages, or excessive latency, the system must degrade gracefully.
- **Rule:** Users are notified with informative messaging and offered immediate access to pre-built, expert-curated starter plans for Weddings, Birthdays, and Community events.

#### 9. Privacy & Minimization of Guest/Personal Data
- **Requirement:** Only collect guest data strictly necessary for event coordination (name, RSVP status, dietary requirement, accessibility need).
- **Rule:** Do not store sensitive personal information (national IDs, credit card numbers, medical histories) on the guest roster.
